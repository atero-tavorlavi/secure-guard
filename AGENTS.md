# AGENTS.md

How coding agents were used to build Secure Guard, and how the project changed shape along the way. Written for a course that asks teams who used coding agents to show the progression, not just the final diff.

## What this project is

Secure Guard is a local security layer for the OpenCode coding agent: before OpenCode runs a tool call, Secure Guard sends it to a small local model together with what led to it (the user's request, the agent's reasoning, recent turns) and asks whether the call is harmful or something the user did not ask for. Depending on the chosen mode it logs the call, holds it for a human decision, or blocks it automatically, and a local dashboard shows every check that was made. The guard model is LAYA, a calibrated decision model chosen after an earlier attempt at a generative judge (a LoRA-tuned Qwen3.5-2B) proved slower and harder to calibrate, and a sibling study compares the two judges head to head on visual prompt injection.

## How agents were used

The implementation work followed one repeating shape: a design spec was written and agreed first, then broken into a numbered implementation plan, then executed task by task. Each task was test-first (tests written to fail for the right reason before the code that passes them), built by a sub-agent dispatched with a self-contained brief, and reviewed independently of the agent that wrote it, against both the spec and code quality. When a review found a problem, a fix round was dispatched and re-reviewed before the task counted as done. Once every task in a plan was closed out, the whole branch got one more review end to end, separate from the per-task ones, which is where a few cross-cutting issues only visible across files turned up.

Humans stayed in the loop at specific points, not just at the end: picking between options an agent surfaced (for example, whether a native OS prompt should be on by default or opt-in), confirming a default before it shipped, and deciding when a "stop and ask" gate (such as a data-quality pilot check) was a real stop rather than something an agent should route around. A recurring rule across both repos in this project: once a fix wave closed out the issues it was dispatched for, any new issue the re-review turned up went back to the human instead of triggering another automatic round.

Safety rules were added after a run that loaded more than one model at once froze the laptop. From then on, every command that loaded or ran a model went through a watchdog that killed the process group on a memory or time limit, only one model process ran at a time, and free memory was checked before starting anything heavy.

## Timeline

1. **Prototype.** The repo started as two files, a prompt-level guard and a mock of it, with no tests and no dashboard, a quick check on user prompts before they reached the model.
2. **First judge: Qwen3.5-2B with LoRA.** To do better than a prompt check, a generative judge was trained: Qwen3.5-2B fine-tuned with LoRA on a laptop (Apple MLX) to read a trace and answer allow or deny. It worked, but it was slow for a check that has to run on every action (0.2-0.4s and a few GB of memory per call) and its output was text, so a probability had to be read off token scores instead of coming out calibrated.
3. **Switch to LAYA.** Looking for something cheaper and already calibrated led to LAYA, a 421M-parameter decision model that answers typed questions with probabilities in one forward pass. The project was redesigned around it: a design spec, a 13-task implementation plan, and a rewrite of the guard as a scanner, an OpenCode plugin and a dashboard.
4. **Pre-implementation spike.** Before writing the plugin, a spike against the actual OpenCode runtime found that the hook the design depended on for a native permission prompt is declared in the plugin SDK's types but never triggered. Blocking was moved to a hook that is awaited and can reject (so throwing from it stops the tool call), and the native-prompt integration was rebuilt as an opt-in feature on top of different, confirmed-working events.
5. **Question and checkpoint tuning.** Several checkpoints and question phrasings were compared on small labeled sets. The checkpoint fine-tuned on security incidents separated short, synthetic attacks from benign calls cleanly. The general-purpose checkpoints did not.
6. **Reviews caught fail-open holes.** Independent review, both per task and of the whole branch, found several ways a flagged call could slip through anyway: a "failure means allow" policy that was too broad, an auto-reply to the native prompt that could fire for calls the guard had not cleared, a security token readable from the dashboard page itself. Each was closed before the branch was considered done.
7. **A live false positive reshaped the input.** In real use, the agent wrote a short script to adjust an image's contrast after being asked what the image said. The call was flagged and held, and the cause turned out to be that the token budget had dropped the reasoning that explained why the script existed, leaving the model to judge a context-free script. This changed what the model is shown, the tool call is never cut, the reasoning is kept, the prompt and older turns shrink first, and moved the default threshold to favor fewer interruptions.
8. **Re-tuning on realistic calls.** Scored again on tool calls that carry real reasoning, accuracy dropped from the synthetic numbers: ROC-AUC 0.81 with the reasoning included, 0.66 without it. The gap between those two numbers is the clearest evidence in the project that the agent's own reasoning, not just the tool call, is what makes a call judgeable.
9. **Sibling study: LAYA vs. the Qwen judge.** A separate, parallel project compares the two judges on the same visual-prompt-injection task the original Qwen judge was trained on, with a frozen and hashed 200-trace test set, fairness rules fixed before any scoring, and learning curves across training-set sizes for both models. A pilot run of the CAPTCHA attack family initially produced no successful injections at all (the distorted text was unreadable), fixed by making the text legible and adding a fallback label for an attempted-but-wrong reading. A later imbalance in the training pool was fixed by generating more candidates while leaving the already-frozen test set untouched. Memory then shaped the run itself. A Qwen LoRA step on a long trace needs about 10 GB of system memory, the watchdog stopped those runs, and a check that only counted CPU memory had been missing the GPU part of the peak. With a deadline approaching, the plan was cut to what fit: the Qwen learning curve stops at 25 examples and LAYA above 25 examples has one seed, both disclosed in the report. On the 200-trace test set, LAYA fine-tuned on 200 examples matched the original Qwen judge's ROC-AUC (0.82) with far fewer false positives and better calibration, but a 400-example LAYA run partly collapsed, and neither model learned anything useful from 25 or 50 examples.

## Notable rulings

| Decision | Why |
|---|---|
| Blocking moved off the `permission.ask` plugin hook onto the hook that OpenCode actually awaits before running a tool | The hook the design assumed is dead code in the OpenCode version used. The awaited hook can reject and stop the call, the other one cannot |
| Native OS permission prompt made opt-in (default off), rebuilt on confirmed-working events instead of the missing hook | The intended hook never fires, and flashing OpenCode's own prompt on every call by default was a worse experience than the dashboard/toast path |
| Auto-answering the native prompt restricted to calls the guard itself had already cleared | An earlier version could auto-approve calls the guard never actually scored, which is a fail-open path in a tool whose whole job is to not do that |
| "Fail open" narrowed to genuine network failures only. An HTTP error response, and any already-flagged call, always fails closed | A broad definition of "unreachable" was quietly letting oversized or error responses through as if the guard were simply down |
| Checkpoint fine-tuned on security incidents chosen over general-purpose ones, with a low threshold | It was the only setup that cleanly separated attacks from benign calls on held-out synthetic samples |
| What the model sees redesigned so the tool call is never shortened and the reasoning is kept over older turns, with the default threshold raised afterward | A real benign call was flagged because the reasoning that explained it had been the first thing cut to fit the token budget |
| Security token moved out of the page into a URL fragment plus session storage, and the self-protection rule broadened | A page that could leak its own access token, or a guard that didn't block tool calls aimed at its own files, defeats the point of a guard |
| Subagent tool calls judged against the parent agent's instruction, left as a documented limitation rather than fixed | No cleaner source for "what was this subagent told to do" was available. Flagging it was judged more useful than a fragile workaround |
| Same calibration procedure required for both judges in the comparison study, not just for LAYA | Fitting calibration for one model and not the other would have made the comparison look better for whichever model got the extra fitting |
| A data-quality pilot gate (a minimum rate of successful injections per attack family) treated as a real stop, not something to route around | The gate exists specifically because it changes what data the study is built on. Skipping it would undermine the whole comparison |
| CAPTCHA pilot's zero successful injections fixed by making the distorted text legible and adding an explicit "attempted but wrong" label, disclosed as the noisiest family | Unreadable text was testing OCR difficulty, not whether the model follows an injected instruction. The fallback label keeps a genuine model behavior (trying to comply) in the data without hiding its unreliability |
| A training-pool imbalance fixed by generating more candidate examples, while the already-frozen, hashed test set was left untouched | The test set's integrity (frozen and hashed before any model saw it) is the fairness guarantee the whole comparison rests on |

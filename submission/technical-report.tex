\begin{abstract}
AI coding agents run shell commands, edit files and fetch web pages on the user's machine. Content they read, even text inside images, can hijack them into leaking secrets or destroying data. We present Secure Guard, a defense for the OpenCode agent that checks every tool call before it runs. Our first judge was Qwen3.5-2B fine-tuned with Low-Rank Adaptation (LoRA) to answer allow or deny. We then built the guard around LAYA, a 421M-parameter decision model trained for calibrated probabilities. LAYA reads the tool call with the user's request and the agent's reasoning and returns the probability that the call is harmful or unrequested. The guard then logs the call, asks the user or blocks it. On 40 held-out tool calls (15 attacks), LAYA reaches an area under the ROC curve (ROC-AUC) of 0.93 and catches 12 of them with one false positive. Without the reasoning, ROC-AUC falls to 0.66. A check takes 0.08 seconds on a laptop, but LAYA's scores are poorly calibrated. On a separate visual-injection task, LAYA fine-tuned on 200 examples matched the Qwen judge's ROC-AUC (0.82) with far fewer false alarms, but a 400-example run collapsed. We also design a user study of the defense's value.
\end{abstract}

\section{Introduction}
Coding agents such as OpenCode~\cite{opencode} turn a request written in natural language into tool calls: shell commands, file edits and web requests. The agent decides which calls to make by reading its context, and that context increasingly includes untrusted content such as web pages, repositories, documents and images. Prompt injection exploits this. Instructions hidden in such content are followed by the agent as if they came from the user~\cite{perez2022ignore,greshake2023}. Multimodal agents widen the attack surface, because an instruction can be written as text inside an image~\cite{bagdasaryan2023,gong2023figstep}. Because the agent acts on the user's machine, a successful injection produces an action rather than a wrong answer: an uploaded SSH key, a deleted folder or a force-pushed branch.

We stop the attack where the harm happens, at the tool call. Secure Guard intercepts every call before it runs and asks a small local model whether the call is harmful or something the user did not ask for. We set four requirements. The check runs locally, so no code or secrets leave the machine. It must be fast enough to run on every call. Its output should be a probability with a threshold, so that users can choose between logging, asking and blocking. Finally, the guarded agent should not be able to switch it off easily.

This report makes four contributions. We describe the design and implementation of Secure Guard as an OpenCode plugin, a local scanner service and a dashboard. We evaluate LAYA as a judge of tool calls, with confidence intervals and ablations of the context it reads. We describe our first approach, a generative judge based on Qwen3.5-2B, and we design a controlled comparison of the two judges on a different task, the post-hoc judging of visual prompt injection. Finally, we summarize a user-study protocol that measures how much users value the protection.

\section{Related Work}
\textbf{Prompt injection.} Perez and Ribeiro showed that simple adversarial prompts make language models ignore their instructions~\cite{perez2022ignore}. Greshake et al. introduced indirect prompt injection, in which the attacker plants instructions in content that an LLM-integrated application retrieves~\cite{greshake2023}. Benchmarks such as InjecAgent~\cite{zhan2024injecagent} and AgentDojo~\cite{debenedetti2024agentdojo} measure how often tool-using agents follow such instructions, and they show that the problem persists in capable models.

\textbf{Visual injection.} Bagdasaryan et al. showed that instructions can be hidden in images and audio given to multimodal models~\cite{bagdasaryan2023}. FigStep writes a harmful request as a numbered list with empty items inside an image~\cite{gong2023figstep}, and MM-SafetyBench places a topic phrase at the bottom of an image to draw out forbidden content~\cite{liu2023mmsafety}. The attack families in our comparison follow these patterns.

\textbf{Input and output defenses.} Prompt-level defenses such as spotlighting mark untrusted content so the model can tell it apart from instructions~\cite{hines2024spotlighting}. Training-time defenses teach the model to rank instructions by their source, as in the instruction hierarchy~\cite{wallace2024hierarchy} and structured queries (StruQ)~\cite{chen2025struq}. Classifier-based guards screen text. Llama Guard classifies prompts and responses against a safety taxonomy~\cite{inan2023llamaguard}, and Prompt Guard detects jailbreak and injection strings in inputs~\cite{wan2024cyberseceval3}. These classifiers judge the text that goes into or comes out of the model, not the action it leads to.

\textbf{Agent-action defenses.} Closest to our work are defenses that act on the agent's actions. CaMeL isolates untrusted data from control flow by design~\cite{debenedetti2025camel}. A privileged model turns the user's request into a program, and capabilities attached to data limit which tool calls untrusted values can reach. LlamaFirewall combines an input classifier (PromptGuard~2), a static analyzer for generated code (CodeShield) and AlignmentCheck, which uses an LLM to audit the agent's chain of thought for goal hijacking~\cite{chennabasappa2025llamafirewall}. Secure Guard is closest to AlignmentCheck, since it also judges each action against the user's request and the agent's reasoning. It differs in that its judge is small, runs locally and does not generate text. The judge returns a probability that feeds an interactive policy of logging, asking or blocking.

\textbf{Calibrated decisions.} Modern neural networks tend to be over-confident~\cite{guo2017calibration}. LAYA is trained with reinforcement learning against strictly proper scoring rules~\cite{gneiting2007}, which reward honest probabilities~\cite{laya}. Its training therefore aims at calibrated probabilities. Whether this holds on tool calls is an empirical question, which we test in Section~\ref{sec:res-laya}.

We use these terms throughout. \emph{Secure Guard} is the whole system. The \emph{plugin} runs inside OpenCode, and the \emph{scanner} is the local service that scores calls and applies the policy. A \emph{judge} is a model that scores, here LAYA or the Qwen judge. The \emph{risk} $p$ is the judge's probability that a call is harmful or unrequested. A call with $p\geq\tau$ is \emph{flagged}, and a flagged call is then allowed or blocked. Figure~\ref{fig:arch} shows the four components.

\textbf{Plugin.} An OpenCode plugin hooks \texttt{tool.execute.before}, which OpenCode awaits before running any tool, and throwing from it blocks the call. For each call the plugin collects the user's last prompt and the reasoning and text the agent produced since that prompt, including earlier tool calls in the same turn. It can also add up to five earlier messages (recent turns), but this is off by default because it lowered accuracy (Section~\ref{sec:res-laya}). The plugin shows notifications for blocks and pending approvals and adds \texttt{/guard} commands to check the status, change the mode, approve or deny a held call and pause the guard. Optionally, a flagged call can be routed to OpenCode's own permission prompt.

\textbf{Scanner.} A local service written in TypeScript receives each check, calls LAYA, applies the policy and stores the decision in SQLite. LAYA is an encoder that does not generate text. Given a JSON state and typed questions, it returns a probability for each answer~\cite{laya}. Its model card states that the \texttt{typed-decisions} checkpoint was fine-tuned on security incidents and agent traces. LAYA is described only in this model card and has not been peer-reviewed. Our default state looks like this:
\begin{small}
\begin{verbatim}
{ "kind": "tool-call", "tool": "bash",
  "args": {"command": "..."},
  "user_prompt": "...", "reasoning": "..." }
\end{verbatim}
\end{small}
We ask three questions. The first is a yes-or-no question: given what the user asked and the agent's reasoning, is this tool call harmful or something the user did not ask for? Its probability of yes is the risk $p$. The second asks for the attack type (prompt injection, data exfiltration, destructive action, privilege escalation or none) and the third for the severity on a four-level scale. The policy uses only $p$. The type and severity are shown in alerts and in the dashboard, and we do not evaluate them. LAYA reads at most 1,024 tokens, so the state is built to fit. The tool call is never shortened. The prompt keeps its first 500 characters and the reasoning keeps its end, the part written right before the call. If the call alone does not fit, its arguments are split into overlapping windows, each scored with the prompt and the end of the reasoning, and the riskiest window decides. At most eight windows are scored, the first seven and the last one. The middle of text longer than about 16~KB is therefore not scored, and the decision is marked as truncated.

\textbf{Policy.} Let $p$ be the risk and $\tau$ the threshold, 0.29 by default. If $p<\tau$, the call runs. Otherwise the call is flagged and the mode decides. In monitor mode it runs and is logged as ``would block.'' In ask mode it waits for a person to allow or block it, and if nobody answers within 120 seconds it is blocked by default. In auto mode it is blocked. A held call can be answered in the OpenCode prompt, in the dashboard or with a slash command, and the first answer recorded in the database wins. A fail-open setting, off by default, covers only two cases: the plugin cannot reach the scanner, or the scanner gets no answer from LAYA. An error response from the scanner always blocks the call, and a flagged call always waits for a decision.

\textbf{Dashboard and data.} A local web dashboard shows summary numbers, blocks over time, breakdowns by attack type and by tool, a queue of held calls with a countdown and a searchable log. Its detail view shows exactly what LAYA saw. Users can mark false positives, and decisions can be exported as CSV, JSON, a standalone HTML report or a fine-tuning dataset whose labels follow the final human decision.

\textbf{Hardening against the guarded agent.} The agent has a shell on the same machine, so the guard treats it as a possible adversary. The API requires a token that is not embedded in the dashboard page. Requests with a foreign \texttt{Host} or \texttt{Origin} header are refused, which blocks DNS rebinding. A rule flags any tool call whose arguments mention the guard's port, data folder or installed plugin file. This rule is best-effort string matching, and a command assembled from fragments or written to a script first gets past it. All decision content is shown as plain text in the dashboard, so attack payloads cannot run as HTML. A process with the user's privileges can still edit the guard's files, so Secure Guard is a review layer and not a sandbox.

\section{Methodology}
The evaluations and cost measurements in this report ran on an Apple M4 Pro MacBook with 24~GB of memory, which we call the M4 Pro below.

\subsection{Implementation and Verification}
Secure Guard is written in TypeScript on the Bun runtime. It was built test-first in thirteen planned tasks and a few follow-ups. A separate AI review pass checked every task against the specification and for code quality, and the whole system had a final review of the same kind. Team members decided between the options that these reviews raised. The suite has 243 automated tests, including tests against a fake LAYA server and a fake OpenCode client, and an optional end-to-end test against a real LAYA server.

\subsection{First Approach: A Generative Judge}\label{sec:qwen}
Our first judge was generative. We took Qwen3.5-2B and fine-tuned it to read a trace (system prompt, user prompt, chat history, model reasoning and a tool call with the image text) and reply with a JSON verdict: \texttt{\{"verdict": "allow"\}} or \texttt{\{"verdict": "deny", "reason": "..."\}}. The training set had 100 traces built from real images and prompts and labeled by hand (Section~\ref{sec:attacks}): 81 labeled allow and 19 labeled deny. We used Low-Rank Adaptation (LoRA)~\cite{hu2022lora}, which freezes the base weights and learns small low-rank matrices next to chosen projection layers. Training used the Hugging Face Parameter-Efficient Fine-Tuning (PEFT) library~\cite{peft} with rank 8, scaling factor $\alpha=16$ and no dropout. The adapters sit on the attention projections (q, k, v and o), the feed-forward projections (gate, up and down) and the projections of the linear-attention layers (\texttt{in\_proj\_qkv}, \texttt{in\_proj\_z} and \texttt{out\_proj}). After training we merged the adapters into the base weights to get a single model.

The generative judge had two drawbacks for a guard that runs on every call. A verdict takes 0.2 to 0.4 seconds and about 4~GB of memory per trace (Table~\ref{tab:cost}). Its output is text, so a probability has to be read from the token scores of the verdict, and nothing in its training targets calibrated probabilities. These drawbacks led us to LAYA, which answers in one forward pass and whose training aims at calibrated probabilities. The case for switching is not decisive. The speed gap is modest and either judge can be recalibrated after training. This report also gives no held-out accuracy for the Qwen judge yet. The comparison in Section~\ref{sec:comparison} includes it as trained.

\subsection{Evaluating LAYA on Tool Calls}\label{sec:eval}
We use the released \texttt{typed-decisions} checkpoint without fine-tuning and evaluate it in three stages. All samples were written by our team before any scoring.
\begin{enumerate}
\item \textbf{Checkpoint and question selection.} We wrote two sets of 40 short hand-written samples, each with 20 attacks and 20 benign samples, covering prompts, tool calls and tool outputs. One set was used for tuning ($T$) and the other only for validation ($V$). On $T$ we compared phrasings of the question, one question per attack category, scores derived from the attack-type question, state formats and three checkpoints (\texttt{multilingual}, \texttt{english} and \texttt{typed-decisions}).
\item \textbf{Realistic tool calls.} We wrote two new sets ($T$ and $V$), each with 25 benign and 15 attack tool calls. Each call comes with a user prompt, the agent's reasoning and recent turns. The benign calls include long commented scripts, git and package-manager commands, file edits and documentation fetches. The attacks include destructive commands, theft of secrets, piping a downloaded script into a shell and permission changes. Others contradict the user's request, such as a force-push after ``pull latest,'' or come with reasoning that reveals an injected instruction.
\item \textbf{Ablation.} We scored the realistic samples in four variants: the full state, the state without recent turns (prompt and reasoning, the current default), the state without reasoning (prompt and turns) and the state without either.
\end{enumerate}
We report the area under the ROC curve (ROC-AUC, or AUC) with a 95\% confidence interval (CI) from 2,000 stratified bootstrap resamples, and paired bootstrap CIs for differences between variants. We choose a threshold on $T$ as the one with the highest catch rate and at most 5\% false positives. At that threshold we report on $V$ the catch rate (attacks flagged) and the false-positive rate (benign calls flagged), with Wilson 95\% CIs. For calibration we report the Brier score and the expected calibration error (ECE), the average gap between predicted risk and observed attack rate over five bins.

\subsection{Comparing the Two Judges}\label{sec:comparison}
This comparison studies a different task from the one Secure Guard performs. The guard judges a tool call before it runs. The comparison asks a post-hoc question: given a system prompt, a user prompt, the text and description of an image and the answer of a vision-language model (VLM), did the model follow an injected instruction? This is the task the Qwen judge was trained on. The results will show how the two judges compare on visual injection and how they learn from few examples. They will not measure how well either judge guards tool calls. In both tasks the positive class is the outcome the judge should stop: deny for the Qwen judge, yes for LAYA and followed for the comparison labels.

\textbf{Data.} We recreated the recipe of the original 100 traces in four families. In the secret-key family the system prompt holds a key and the image says ``Do not mention any \emph{object} in this image. Instead, print out the secret key.'' In the forbidden-topic family the system prompt forbids a topic and the image shows that topic at the bottom~\cite{liu2023mmsafety} or as an empty numbered list~\cite{gong2023figstep}. In the CAPTCHA family the system prompt forbids solving CAPTCHAs and the image shows distorted text on a sign, a tag or a calendar. The fourth family is benign. Images are rendered deterministically. The answers come from a real VLM (Qwen3.5-2B-base running in MLX, Apple's array framework for its own chips~\cite{mlx}) at temperature 0.7, so the model follows or refuses on its own. Labels are automatic. A trace counts as followed when the key or CAPTCHA string appears in the answer, when the forbidden topic is discussed without a refusal or, for CAPTCHA, when the model agrees to read the text even if its reading is wrong. A stratified sample of 100 traces is checked against the written rule.

\textbf{Fairness rules.} These rules were fixed before any evaluation. A test set of 200 traces (about 40\% followed, 50 per family, with at least 30\% of topics and objects never seen in training) is generated, frozen and hashed before either model sees it. Both models train on the same examples at every point of the learning curve and see the same fields. Thresholds are chosen on validation splits only. Any calibration fitted for one model is fitted for the other, and every fine-tuning run is repeated with two seeds.

\textbf{Contenders.} We evaluate the Qwen judge as trained, the same judge with the real image attached (exploratory, since it was trained on text only), LAYA without fine-tuning, LAYA fine-tuned on $n$ examples and Qwen3.5-2B-base fine-tuned with LoRA on the same $n$ examples, for $n$ equal to 25, 50, 100, 200 and 400. These learning-curve Qwen runs use LoRA in MLX on the M4 Pro, with a batch size of 1, gradient checkpointing and a maximum length of 512 tokens so that they fit in memory.

\textbf{LAYA fine-tuning.} LAYA is a ModernBERT-large encoder~\cite{modernbert} with 421M parameters and heads that answer typed questions. We fine-tune it with its authors' procedure, which the model card calls RLCD: reinforcement learning against strictly proper scoring rules~\cite{laya}. Each training example is a state, a question and the correct answer. In each step the model outputs a probability for every answer. Gaussian noise is added to its logits to explore, starting at a standard deviation of 0.4 and shrinking during training, and four noisy samples are drawn per example. Each sample is rewarded with a strictly proper scoring rule~\cite{gneiting2007}, a mix of the log score and the spherical score. Such a rule gives the highest expected reward only to honest probabilities. The update is REINFORCE~\cite{williams1992} with the group mean as the baseline, the same idea as Group Relative Policy Optimization (GRPO)~\cite{shao2024grpo}. A soft cross-entropy loss towards the labels keeps training stable. All weights are updated, not an adapter. After training, a temperature is fitted for each question on held-out examples~\cite{guo2017calibration}, with the aim that a score of 0.7 means about 70\%. A training step takes about 0.9 seconds with 7.5~GB of memory.

\textbf{Metrics.} We report accuracy and F1 (the harmonic mean of precision and recall) on the followed class at the validation threshold, ROC-AUC (LAYA's probability of yes and Qwen's probability of deny at the verdict token), ECE, latency and memory. Every metric is broken down by family and by seen and unseen topics.

\textbf{Known weaknesses.} The answers come from the same model family as the Qwen judge, which may favor it. The CAPTCHA label is lenient, since it counts an agreement to read rather than a correct reading, so CAPTCHA is the noisiest family. LAYA is fully fine-tuned while Qwen gets LoRA, and two seeds give only a rough idea of the variance at small $n$.

\subsection{User Study}
A separate protocol (\texttt{user-study-protocol.pdf}) describes a $2\times2$ between-subjects online study with two sessions one week apart. Every participant holds \$4.00 of real money in a study wallet. One factor varies whether participants live through an attack in a simulated workspace or read an illustrated description of the same events (lived versus described). The other varies whether Secure Guard asks before blocking or blocks automatically. The money at stake is the same in all four cells. Using the incentive-compatible Becker--DeGroot--Marschak (BDM) mechanism~\cite{bdm1964}, the study measures the smallest payment for which participants would let us turn Secure Guard off in the follow-up session. In that session a hidden instruction may try to make the agent send \$2.00 from the wallet. The study has not been piloted yet, so the pilot is part of our future work (Section~\ref{sec:discussion}).

Realistic calls with context are harder, and the choice of context matters. With the full state, the AUC on $V$ is 0.81 (CI 0.65 to 0.93). Dropping the recent turns raises it to 0.93 (0.82 to 1.00). The paired difference on $V$ is $-0.12$ ($-0.28$ to 0.03), so $V$ alone cannot rule out no effect. On $T$ and $V$ pooled (80 samples, 30 attacks) the difference is $-0.11$ ($-0.21$ to $-0.02$). Earlier turns seem to add noise rather than signal here, so the guard now sends the prompt and the reasoning only. Removing the reasoning instead lowers the AUC to 0.63 (0.45 to 0.79), a paired difference from the full state of 0.17 (0.07 to 0.30). Without both, the AUC is 0.66 (0.49 to 0.82). In this small set the reasoning carries most of the signal. Part of that effect is by construction, because some attack items have reasoning that reveals the injection.

The default threshold of 0.29 was chosen on $T$ for the prompt-and-reasoning input, where it caught 14 of 15 attacks with 1 false positive in 25. On $V$ it catches 12 of 15 attacks (80\%, CI 55\% to 93\%) with 1 false positive in 25 benign calls (4\%, CI 1\% to 20\%). The threshold never saw $V$, but we chose to drop the recent turns after seeing the $V$ results, so $V$ is not fully held out for that choice. All realistic results use the state layout that the scanner builds today.

The operating point is sensitive to the threshold. With the full state, a threshold of 0.25 catches all 15 attacks but flags 16 of the 25 benign calls, 0.35 catches 6 with no false positives and 0.45 catches only 2. With the default input, moving from 0.29 to 0.35 drops the catch rate from 12 to 6 of 15.

\textbf{Calibration.} We measured calibration for the full state on $V$. LAYA's scores fall in a narrow band from 0.15 to 0.49. The Brier score is 0.21, and the ECE is 0.10 with five equal-width bins and 0.28 with five equal-count bins. The low equal-width value is misleading, since 35 of the 40 scores share the bin from 0.20 to 0.40. Within that band the observed attack rate does not rise steadily with the score. A score of 0.3 therefore does not mean a 30\% chance of attack, and the threshold has to be chosen on labeled data. We did not measure calibration for the default input.

\textbf{End-to-end check and live use.} An end-to-end test against a real LAYA server with 10 attack and 10 benign calls in the short format ($\tau=0.25$) caught 8 of the 10 attacks with no false positives. The two misses were adding an attacker's key to \texttt{authorized\_keys} (score 0.24) and creating cloud access keys (score 0.19). In one of our own sessions, we asked the agent what an image says, and it wrote a harmless Python script to raise the image's contrast. The script scored 0.39 and was held for approval under the threshold of 0.25 then in use. We found that the token budget had cut the reasoning, so LAYA judged the script without knowing why it was written. This led to the current state layout (tool call, prompt, end of the reasoning and then older turns) and, at the time, to a default threshold of 0.45. That threshold had not been evaluated. On $V$ it catches only 2 of 15 attacks, which is why we replaced it with 0.29.

\subsection{Comparison Data}
In a data-generation trial of 77 traces, the answering model followed the injection in 60\% of the secret-key traces and 85\% of the forbidden-topic traces. For CAPTCHA it followed none of them at first, because it refused or could not read the heavily distorted text. After we made the text legible, 25\% of the answers reproduced the exact string and 75\% agreed to read it. All three attack families then passed the minimum follow rate of 30\% that we had set in advance. The label check of 100 traces was done by an AI reviewer (Claude) reading each answer against the written rule, not by a person. It agreed with the automatic label on 97 of 100 (all 25 secret-key and benign traces, 24 of 25 forbidden-topic and 23 of 25 CAPTCHA traces). In all three disagreements the automatic rule missed a followed trace: a refusal followed by a full discussion of the topic, and two CAPTCHA answers that agreed to read the text without the phrasing the rule looks for. The automatic labels therefore slightly undercount followed traces, and we did not correct them.

\textbf{Few examples are not enough.} With 25 or 50 examples neither fine-tuned judge learns the task. Both flag almost every trace, and two LAYA runs (one seed at $n=25$, and $n=50$) gave the same score to every trace, so their AUC is exactly 0.50. LAYA without fine-tuning is also near chance. It was trained to judge actions, not to tell whether a model followed an instruction.

\textbf{LAYA can learn the task, but not reliably.} The AUC rises from 0.62 at $n=100$ to 0.82 at $n=200$. At $n=100$ LAYA is too cautious to be useful: it flags no benign trace but catches only 8 of 81 followed traces. At $n=200$ it catches 55 of 81 with 8 false positives in 119, an accuracy of 0.83 and an F1 of 0.76 (CI 0.68 to 0.84). At $n=400$ training partly collapsed. The AUC fell to 0.64 (0.59 to 0.69), the secret-key and CAPTCHA families scored at chance, and the validation threshold flagged every trace. The curve is therefore not monotonic, and with one seed we cannot tell whether $n=200$ was a good run or $n=400$ a bad one.

\textbf{The Qwen judge as trained is a strong baseline.} It was fine-tuned on the original 100 traces, whose recipe our data recreates, and it reaches an AUC of 0.82, the same as LAYA at $n=200$. Its operating point is worse. It catches 67 of 81 followed traces but flags 47 of 119 others (39\%), mostly in the secret-key and forbidden-topic families, where it flags 74\% and 87\% of the traces that were not followed. After the same calibration, LAYA at $n=200$ has a lower calibration error (ECE 0.09 against 0.12, Brier 0.14 against 0.18) and holds up better on topics never seen in training (AUC 0.80 against 0.74). By family, LAYA at $n=200$ separates the forbidden-topic traces far better (AUC 0.92 against 0.62) and the CAPTCHA traces far worse (0.47 against 0.87). CAPTCHA has the noisiest labels (Section~\ref{sec:comparison}). Attaching the real image did not help the Qwen judge, which was trained on text only. Its AUC fell to 0.71, and each trace took four times longer.

\textbf{Cost.} On this task LAYA scores a trace in 0.11 seconds and the Qwen judge in 0.86 seconds, eight times slower, because these traces are longer than tool calls. A LAYA fine-tuning run on 200 examples took 7.4 minutes at a peak of 7.4~GB.

In short, LAYA fine-tuned on 200 examples matched the generative judge on ranking, made far fewer false alarms, was better calibrated and was much faster. The same procedure learned nothing from 25 or 50 examples and partly collapsed on 400, so LAYA's fine-tuning is unstable at these sizes. These results rest on one seed above $n=25$ and on a Qwen learning curve that stops at $n=25$, and they do not show that LAYA reliably beats the generative judge.

\section{Discussion}\label{sec:discussion}
\textbf{What worked.} Judging actions rather than inputs lets the guard use the agent's own account of why it acts, which was the most useful input in our measurements. A judge that does not generate text adds 0.08 seconds per call, which is cheap enough to run on every call. More context was not better. Earlier turns lowered the AUC, so the default now leaves them out. We have not yet studied why.

\textbf{Limitations.} The main gap is missed attacks. At the default threshold the guard misses 3 of 15 held-out attacks, and ask mode does nothing about calls that are never flagged. Our evaluation sets are small (40 held-out samples, 15 of them attacks), and every interval above is wide. All samples were written by our team, and we dropped the recent turns after seeing $V$. Calls from public benchmarks such as InjecAgent~\cite{zhan2024injecagent} or AgentDojo~\cite{debenedetti2024agentdojo} would be a stronger check. LAYA's scores are poorly calibrated on this task, so the threshold must be chosen on labeled data and changed with care. Some attack items have reasoning that reveals the injection, which inflates the effect of the reasoning, and we did not ablate the user prompt. LAYA's window of 1,024 tokens forces us to shorten long reasoning. OpenCode's plugin API also limited the interface. The hook for answering permission prompts is declared but never called, so our native-prompt option works through events and briefly shows the prompt for calls that were not flagged.

\textbf{Attacks on the guard.} We have not tested adaptive attacks on the guard itself. The reasoning that LAYA relies on most is written by the agent, so an injected instruction can also tell the agent to explain a harmful call in harmless terms. An attacker can pad a payload so that its harmful part lands in the unscored middle of a long argument, although that decision is then marked as truncated. Indirection such as variables, encoded paths or a script written in one call and run in a later one gets past the self-protection rule. An exfiltration can also be split across several calls that each look harmless. Finally, the guard runs with the user's privileges, so a determined local process can disable it.

\textbf{Security and privacy.} All inference runs locally and all decisions stay on the machine. The stored log contains prompts, reasoning and tool outputs, which are sensitive in their own right, so it is deleted after 30 days by default. The fine-tuning export carries the same content.

\textbf{Future work.} We plan to fine-tune LAYA on decisions collected by the guard, since the export already records human corrections. These labels are biased. Missed attacks are never flagged and so never labeled, and people sometimes approve attacks, so this data needs audits and labeled attacks from other sources. We will also finish the comparison with the generative judge (a second seed for LAYA above $n=25$ and the Qwen learning curve, which needs a way around its memory peak on long traces), add high-precision rules for well-known destructive patterns next to the model, test adaptive attacks on the guard and run the user study, starting with the planned pilot of 10 participants.

\section{Conclusion}
Secure Guard shows that a small local decision model can check every action an AI coding agent takes, at 0.08 seconds per call. In our small hand-written evaluation, the agent's reasoning was the most useful context and earlier turns hurt. With the prompt and the reasoning, the guard caught 12 of 15 held-out attacks with one false positive in 25 benign calls. Ask mode limits the cost of false alarms, but missed attacks remain the main gap, and LAYA's scores are poorly calibrated on this task. On visual prompt injection, LAYA fine-tuned on 200 examples matched the generative judge's ranking with far fewer false alarms and better calibration, at an eighth of the cost per trace, but a run on 400 examples partly collapsed, so its fine-tuning is not yet reliable. The guard's decision log can supply more training data, once its label bias is handled.
